## 핵심 요약

<strong>객체지향 언어(OOP: Object-Oriented Programming)</strong>는 데이터(상태)와 기능(행위)을 하나로 묶은 <strong>'객체(Object)'</strong>들을 조립하여 프로그램을 구축하는 프로그래밍 패러다임이다.

<strong>Java</strong>는 클래스(Class)를 최우선 단위로 설계하고 캡슐화, 상속, 다형성, 추상화를 언어 차원에서 강제 및 보장하므로 대표적인 객체지향 언어다.


<NotionDivider />

<a id="1-객체지향-언어oop란-무엇인가"></a>

## 1. 객체지향 언어(OOP)란 무엇인가?

프로그램을 단순한 명령어의 순차적 실행이 아니라, <strong>현실 세계의 개념을 모델링한 '객체(Object)'들의 상호작용</strong>으로 바라보는 방식이다.


```text
[객체 (Object)] = 상태 (State / 필드) + 행위 (Behavior / 메서드)
```

<a id="oop의-4대-핵심-기둥-four-pillars"></a>

### OOP의 4대 핵심 기둥 (Four Pillars)

1. <strong>캡슐화 (Encapsulation)</strong>: 데이터와 메서드를 클래스로 묶고, 접근 제어자(`private`)를 통해 외부의 부적절한 직접 접근을 차단함.
1. <strong>상속 (Inheritance)</strong>: 부모 클래스의 자원과 기능을 자식 클래스가 재사용 및 확장함 (`extends`).
1. <strong>다형성 (Polymorphism)</strong>: 하나의 인터페이스나 메서드가 상황에 따라 서로 다른 동작을 수행함 (오버라이딩, 오버로딩).
1. <strong>추상화 (Abstraction)</strong>: 복잡한 내부 구현 세부사항은 숨기고, 필요한 핵심 인터페이스만 외부에 노출함 (`interface`, `abstract`).

## 2. Java는 왜 객체지향 언어인가?

Java는 처음부터 객체지향 철학을 바탕으로 설계된 언어다.

1. <strong>클래스 중심 설계 (Class-Centric Design)</strong>:
- Java에서는 클래스 외부에 독립적인 단독 함수나 전역 변수를 작성할 수 없다. 모든 코드와 데이터는 반드시 클래스 내부(`class`)에 존재해야 한다.

1. <strong>4대 객체지향 특징의 완벽한 언어적 보장</strong>:
- `private`, `protected`, `public` 키워드로 <strong>캡슐화</strong>를 강제한다.
- `extends` 키워드로 단일 <strong>상속</strong>을 지원한다.
- `interface`와 `@Override`를 통해 높은 수준의 <strong>다형성과 추상화</strong>를 구현한다.

1. <strong>풍부한 객체지향 오픈소스 생태계</strong>:
- 객체지향 디자인 패턴(Gang of Four)과 SOLID 원칙을 가장 깔끔하게 적용할 수 있는 표준 환경을 제공한다.

## 3. 프로그래밍 패러다임 비교 (POP, OOP, Pascal, FP)

프로그래밍의 역사는 문제 해결 방식에 따라 여러 패러다임으로 진화해 왔다.


```text
[발전 흐름]
절차지향 (POP / C) ──> 구조적 (Pascal) ──> 객체지향 (OOP / Java) ──> 함수형 (FP / Haskell)
```

<a id="1-pop-procedure-oriented-programming-절차지향"></a>

### 1) POP (Procedure-Oriented Programming, 절차지향)

- <strong>개념</strong>: 프로그램의 실행 순서(절차)와 <strong>함수(Procedure)</strong> 단위로 코드를 작성하는 방식 (예: C 언어).
- <strong>특징</strong>: 데이터와 함수가 분리되어 있어 프로젝트가 커지면 데이터 변경 시 모든 함수를 수정해야 하는 유지보수 한계가 발생한다.
<a id="2-oop-object-oriented-programming-객체지향"></a>

### 2) OOP (Object-Oriented Programming, 객체지향)

- <strong>개념</strong>: <strong>객체(Object)</strong>를 단위로 상태와 행위를 묶어 모듈화하는 방식 (예: Java, C++).
- <strong>특징</strong>: 재사용성, 확장성, 유지보수성이 뛰어나 대규모 엔터프라이즈 시스템 구축의 표준으로 자리 잡았다.
<a id="3-파스칼-프로그래밍-pascal-structured-programming"></a>

### 3) 파스칼 프로그래밍 (Pascal & Structured Programming)

- <strong>개념</strong>: 1970년 닉클라우스 비르트가 만든 언어로, <strong>구조적 프로그래밍(Structured Programming)</strong>의 시초다.
- <strong>특징</strong>: 무분별한 `goto` 문 사용을 금지하고, `begin-end` 블록과 조건문/반복문, 서브루틴을 도입하여 코드의 흐름을 통제 가능한 구조로 만들었다. Modern 언어 제어문의 뿌리가 됨.
<a id="4-fp-functional-programming-함수형-프로그래밍"></a>

### 4) FP (Functional Programming, 함수형 프로그래밍)

- <strong>개념</strong>: <strong>순수 함수(Pure Function)</strong>와 <strong>불변성(Immutability)</strong>을 바탕으로 데이터 변형(Side-effect)을 최소화하는 방식 (예: Haskell, Scala, Modern JS / Java 8+ Stream).
- <strong>특징</strong>: 함수를 1급 객체(First-Class)로 다루며, 멀티스레드 동시성 환경에서 상태 변경 에러가 적어 최근 다시 주목받고 있다.

## 5. 언어론적 심층 고찰: "Java, C, Python으로 다른 패러다임 코드 작성이 불가능한가?"

<a id="1-기술적-가능성-구현-자체는-모두-가능하다"></a>

### 1) 기술적 가능성: "구현 자체는 모두 가능하다"

현대의 대부분의 범용 프로그래밍 언어는 튜닝 완전(Turing Complete)하므로, 다른 패러다임의 코드 구조를 기술적으로 흉내 내거나 구현하는 것은 <strong>가능하다</strong>.

- <strong>C 언어에서의 객체지향 구현</strong>: 구조체(`struct`)와 <strong>함수 포인터(Function Pointer)</strong>를 결합하여 가상 함수 테이블(VTable)을 수동 구성하면 캡슐화와 다형성을 흉내 낼 수 있다 (실제 리눅스 커널의 VFS 드라이버나 GNOME의 GObject가 이 방식을 사용함).
- <strong>Java에서의 절차지향 / 함수형 구현</strong>: 클래스 내에 모든 상태와 메서드를 `public static`으로 선언하고 순차 호출하면 절차지향으로 동작하며, Java 8+의 람다와 함수형 인터페이스로 함수형 프로그래밍을 구사할 수 있다.
- <strong>Python에서의 다중 패러다임</strong>: 파이썬은 태생부터 절차지향, 객체지향, 함수형 기법을 자유롭게 혼용할 수 있는 멀티 패러다임 언어다.

<NotionDivider />

<a id="2-언어의-지향점design-goal과-어긋날-때-발생하는-관리-영역의-구멍"></a>

### 2) 언어의 지향점(Design Goal)과 어긋날 때 발생하는 '관리 영역의 구멍'

구현이 "가능하다"는 것과 그것이 "올바른 엔지니어링인가"는 완전히 다른 문제다. 각 언어가 탄생한 <strong>본래의 개발 목적과 지향점</strong>을 벗어나 억지스러운 패러다임으로 코드를 작성하면 심각한 시스템적 부작용이 발생한다.


```text
[ C 언어에서 무리한 OOP 흉내 시 ]
 ├─ malloc / free 수동 관리 ➔ 객체 소멸 주기 누락 시 치명적인 메모리 누수(Memory Leak) & 시스템 다운
 └─ 문법적 지원 부재 ➔ 함수 포인터 남발로 코드 간 연관성 추적 불가 (스파게티 코드화)

[ Java에서 무리한 절차지향(All static) 작성 시 ]
 ├─ 객체지향 캡슐화 상실 ➔ 전역 가변 상태 공유로 멀티스레드 동시성 데이터 오염(Race Condition)
 └─ 다형성/인터페이스 미활용 ➔ 변경 발생 시 시스템 전반의 코드 수정 비용 폭증
```

1. <strong>C 언어에서 섣부른 객체지향 흉내의 위험</strong>:
- C 언어는 가비지 컬렉터(GC) 없이 메모리를 직접 제어하는 언어다. 객체지향을 흉내 내려고 동적 메모리 할당과 복잡한 함수 포인터를 남발하다 보면, 객체 해제 타이밍을 놓쳐 <strong>심각한 메모리 누수(Memory Leak)</strong>로 서버가 OOM/Crash되는 참사를 초래한다.
- 또한, 언어 컴파일러가 타입과 상속 관계를 직접 보장해주지 않기 때문에 기능이 고도화될수록 <strong>코드 간의 연관성과 호출 흐름을 파악하기가 극도로 어려워져 유지보수가 붕괴</strong>된다.

1. <strong>Java에서 무분별한 절차적(All Static) 코딩의 위험</strong>:
- 객체의 라이프사이클을 무시하고 전역 static 메서드와 변수로만 코드를 작성하면, 객체지향이 제공하는 캡슐화와 다형성의 이점을 완전히 잃게 되며 멀티스레드 환경에서 치명적인 상태 오염을 유발한다.

### 3) 최종 결론: 언어의 역사, 배경, 생태계 이해의 중요성

> 💡 <strong>소프트웨어 아키텍트의 교훈</strong>:


<NotionIndent>

프로그래밍 언어를 선택하고 코드를 작성할 때는 단순히 <em>"이 문법으로 짤 수 있는가?"</em>라는 기능적 가능성만 보아서는 안 된다.

<strong>해당 언어의 탄생 역사, 메모리 모델, 런타임 특성, 그리고 커뮤니티가 지향하는 생태계의 철학</strong>을 명확히 이해하고, 그 <strong>언어의 지향점에 가장 부합하는 패러다임을 준수하여 설계</strong>할 때만이 시스템 안정성과 지속 가능한 유지보수성을 확보할 수 있다.


</NotionIndent>
