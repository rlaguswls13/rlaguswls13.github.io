## 1. GC에 대한 정의

<a id="11-gc-메모리를-정리해-주는-것"></a>

### 1.1 GC = 메모리를 정리해 주는 것

GC(Garbage Collection)는 프로그램이 더 이상 접근할 수 없는(**도달 불가능, unreachable**) 객체가 점유한 **힙(Heap)** 메모리를 자동으로 회수하는 JVM 기능입니다. 회수 대상 판정은 **참조 카운팅이 아니라 GC Root로부터의 도달 가능성(reachability)**을 기준으로 하므로, 서로만 참조하는 순환 참조 덩어리도 루트에서 닿지 않으면 통째로 회수됩니다. GC Root는 실행 중인 스레드의 스택 지역 변수·매개변수, 클래스의 `static` 필드, JNI 전역 참조 등입니다. 덕분에 개발자는 C/C++처럼 `free`/`delete`로 해제 시점을 직접 관리할 필요가 없고, 이중 해제·dangling pointer 같은 결함이 언어 차원에서 사라집니다. 대신 회수 시점 계산 동안 애플리케이션 스레드가 멈추는 **Stop-The-World(STW)** 비용을 감수합니다.

<a id="22-참고-5영역-심화"></a>

### 2.2 참고: 5영역 심화

JVM 명세는 Runtime Data Areas를 5개로 규정합니다 — **Heap, Method Area(HotSpot 구현상 Metaspace), PC Register, JVM Stack, Native Method Stack**. 이 중 **Heap과 Method Area는 전 스레드가 공유**하고, **PC Register·JVM Stack·Native Method Stack은 스레드마다 1개씩** 갖습니다(공유 2 + 스레드별 3). Java 8에서 클래스 메타데이터가 PermGen에서 네이티브 메모리의 Metaspace로 옮겨졌고 PermGen은 완전히 제거되었습니다.

<a id="23-gc가-관리하는-영역-나머지의-라이프사이클"></a>

### 2.3 GC가 관리하는 영역 / 나머지의 라이프사이클

- **GC 관리 대상**: **Heap**(주무대 — Young은 자주, Old는 드물게 회수), **Metaspace**(클래스 언로딩이 일어날 때만 제한적으로).
- **GC 비관리**: **JVM Stack / Native Method Stack / PC Register**. 이들은 **메서드에 진입하면 프레임을 push, 반환하면 프레임을 pop**하는 스코프 기반으로 자동 소멸하므로, 죽은 값을 하나하나 추적할 필요가 없습니다.
- 다만 스택은 **힙 GC의 GC Root** 역할을 합니다. "스택 자체는 GC가 관리하지 않지만, 스택 프레임의 참조가 힙 객체의 생존을 결정한다"로 요약됩니다.

## 3. GC의 메커니즘

<a id="31-가장-기본적인-메커니즘"></a>

### 3.1 가장 기본적인 메커니즘

기본 알고리즘은 **Mark → Sweep → (Compact)**입니다. **Mark**는 GC Root에서 출발해 도달 가능한 객체에 "살아있음"을 표시하고, **Sweep**는 표시되지 않은 객체의 공간을 회수하며, **Compact**(선택적)는 살아있는 객체를 한쪽으로 몰아 단편화를 제거합니다. 새 객체가 몰리는 **Young 영역은 Mark-Sweep 대신 Copying(살아있는 객체만 다른 공간으로 복사)**을 써서, 비용이 죽은 객체 수가 아니라 **살아남은 객체 수에 비례**하게 만듭니다("대부분의 객체는 금방 죽는다"는 weak generational hypothesis 덕에 효율적). 수집 범위에 따라 **Minor GC(Young) / Major GC(Old) / Full GC(전체)**로 나뉘며, Full GC가 잦으면 심각한 튜닝 신호입니다. 모든 수집은 최소한의 STW를 동반합니다.

<a id="33-parallel-gc-g1gc-zgc-next"></a>

### 3.3 Parallel GC → G1GC → ZGC → next?

- **Parallel GC**: STW 중에 여러 GC 스레드가 함께 수집. **처리량(throughput) 최대화**가 목표이며 개별 STW는 길 수 있음.
- **G1 GC**: 힙을 크기가 같은 다수의 **Region**(1~32MB)으로 쪼개고, **`XX:MaxGCPauseMillis`로 목표 pause 시간을 지정**하면 회수 이득이 큰 Region부터 점진적으로 압축 수집. 현재 표준 기본 GC.
- **ZGC**: **colored pointer + load barrier**로 마킹·압축의 대부분을 concurrent 처리. **힙 크기와 무관하게 1~10ms 수준의 pause**, TB급 힙 지원.
- **next = Generational ZGC**: 저지연을 유지하면서 **세대 가설을 다시 결합**해 처리량과 메모리 효율을 회복.
발전 방향
**처리량 우선(Parallel) → 저지연 시도(CMS, 단편화 문제) → Region 기반 + pause 목표(G1) → 힙 크기와 무관한 초저지연(ZGC) → 저지연 + 대용량 힙 + 세대 효율 복원(Generational ZGC)**.

## 4. GC를 고려한 개발 시 유의점

<a id="41-대용량-트래픽-처리"></a>

### 4.1 대용량 트래픽 처리

부하가 커지면 결국 `OutOfMemoryError`(주로 힙)가 더 자주 나지만, 근본 원인은 대개 "메모리 누수"가 아니라 **유입 속도가 처리 속도를 앞서는데 그 차이를 무제한(unbounded) 버퍼가 흡수하다 터지는 것**입니다. 다운스트림(DB·외부 API)이 느려지면 리틀의 법칙(L = λ × W)대로 in-flight 객체 수가 늘어 "요청 수는 그대로인데 힙이 터지는" 현상이 나타납니다. 대응은 **모든 큐·풀·동시 실행 수에 상한(limit)을 두고, 상한을 넘으면 거절하거나 지연시키는 것(backpressure)**입니다. 무제한 큐(`new LinkedBlockingQueue<>()`), 무제한 스레드풀(`newCachedThreadPool()`)은 붕괴 시점을 뒤로 미룰 뿐이며, 지연된 OOM은 진단이 더 어렵습니다. 상세: [Java - 대용량 트래픽·비동기 병렬 환경의 메모리·리소스 한계 관리](https://app.notion.com/p/Java%20-%20%EB%8C%80%EC%9A%A9%EB%9F%89%20%ED%8A%B8%EB%9E%98%ED%94%BD%C2%B7%EB%B9%84%EB%8F%99%EA%B8%B0%20%EB%B3%91%EB%A0%AC%20%ED%99%98%EA%B2%BD%EC%9D%98%20%EB%A9%94%EB%AA%A8%EB%A6%AC%C2%B7%EB%A6%AC%EC%86%8C%EC%8A%A4%20%ED%95%9C%EA%B3%84%20%EA%B4%80%EB%A6%AC).

<a id="42-세대별-gc를-고려한-bulk-처리"></a>

### 4.2 세대별 GC를 고려한 bulk 처리

대량 데이터를 한 번에 `List`로 materialize하면, 단명할 수도 있었던 대용량 객체가 Young 영역을 넘겨 **Old로 조기 승격(premature promotion)**되고, 이는 Full GC와 (G1의 경우) humongous allocation 부담을 유발합니다. 대응은 **청크 단위 스트리밍 처리**입니다 — JDBC `fetch size` 조정, `Stream`/커서 기반 순회, 배치 크기 상한, 불필요한 중간 컬렉션 제거. 원칙은 "객체를 **짧게 살고 작게**" 만들어 Young GC 단계에서 회수되도록 하는 것입니다. 결과 집합·응답 바디를 전량 버퍼링하지 않는 것도 같은 맥락입니다.

<a id="43-비동기병렬-제한-관리"></a>

### 4.3 비동기·병렬 제한 관리

동시성 도구는 편리하지만 **동시 진행 수에 상한이 없으면 in-flight 객체가 힙에 쌓입니다.** `CompletableFuture` 팬아웃은 수천 개 작업을 한꺼번에 만들지 말고 배치로 분할하거나 `Semaphore`로 제한하고, `parallelStream`은 공용 `ForkJoinPool`을 공유하므로 블로킹 작업에 쓰지 않습니다. 리액티브(Project Reactor)의 `onBackpressureBuffer`는 반드시 상한 용량을 지정하고 `limitRate(n)`으로 demand를 조절합니다. **가상 스레드(Java 21)는 "스레드 수" 병목은 없애지만**, DB 커넥션·외부 API rate limit 같은 **다운스트림 리소스의 동시 사용량은 여전히 `Semaphore` 등으로 제한**해야 합니다. 기능별로 풀·세마포어를 분리하는 Bulkhead도 함께 고려합니다.

<a id="44-싱글톤라이프사이클-관리"></a>

### 4.4 싱글톤·라이프사이클 관리

상세 노트 4개에서 정면으로 다루지 않은 주제로, GC Root에 준하는 **강한 참조를 오래 쥐고 있는 객체**가 사실상의 누수를 만드는 패턴입니다.

- **싱글톤 / `static` 필드 / 애플리케이션 컨텍스트**가 참조하는 객체는 GC Root에 준하는 강한 참조여서 **앱이 종료될 때까지 회수되지 않습니다.** 여기에 캐시를 무한정 담으면 그대로 누수입니다. 
캐시(임시참조 - 동적참조)는 크기·TTL을 제한(LRU, Caffeine 등)하거나 `WeakHashMap`/`SoftReference`로 참조 강도를 낮춥니다.
- **`ThreadLocal`**은 스레드풀에서 스레드가 재사용되므로, 사용 후 **`remove()`를 호출하지 않으면 그 스레드가 사는 내내 값이 누적**됩니다. 요청 처리 후 정리가 필수입니다.
- **리스너 / 콜백 / 이벤트 핸들러**는 **등록했으면 반드시 해제**합니다. 해제하지 않으면 등록 주체가 등록 대상을 계속 참조합니다.
- **스프링 빈은 기본 싱글톤 스코프**입니다. 빈에 요청 단위 가변 상태를 필드로 두지 않고, prototype/request 스코프는 소멸 콜백 지원에 한계가 있음을 인지합니다.
- **ClassLoader 누수**: 웹앱 리로딩 시 이전 ClassLoader가 어디선가 참조되면, 그 로더가 로드한 모든 클래스가 Metaspace에 잔존해 `OutOfMemoryError: Metaspace`로 이어집니다.
