## 핵심 요약

- 한국어 구어체에서 흔히 "오버라이트(overwrite)"라 부르지만, Java의 정확한 용어는 **오버라이드(Override, 재정의)**입니다. `overwrite`(덮어쓰기)는 파일이나 변수 값을 물리적으로 지우고 다시 쓰는 별개의 개념이며, Java 언어 명세(JLS)에는 등장하지 않습니다.
- **오버라이드(Override)**: 상위 클래스가 정의한 메서드를 하위 클래스가 **같은 시그니처로 다시 정의**하는 것. **상속(또는 인터페이스 구현) 관계에서만** 성립하며, 호출 대상은 **런타임의 실제 객체 타입**으로 결정됩니다(동적 바인딩).
- **오버로드(Overload)**: **같은 이름의 메서드를 매개변수 목록만 다르게** 하여 여러 개 정의하는 것. 상속과 무관하며, 호출 대상은 **컴파일 시점의 인자 타입**으로 결정됩니다(정적 바인딩).

<a id="0-추상화-계층-구분선-scoping-boundary"></a>

## 0. 추상화 계층 구분선 (Scoping Boundary)

- **언어 명세 계층 (Java Language Specification)**: 오버라이드/오버로드가 "무엇인가"를 규정하는 계층. 시그니처, 접근제어자, 반환형, 예외 규칙, 메서드 하이딩 등은 모두 JLS §8.4.8(Inheritance, Overriding, Hiding), §8.4.9(Overloading), §15.12(Method Invocation)에서 정의됩니다.
- **컴파일러 계층 (javac)**: 오버로드 해석(어느 메서드를 호출할지 결정), `@Override` 검증, 반환형만 다른 정의에 대한 컴파일 에러 판정이 이뤄지는 계층.
- **런타임 계층 (JVM)**: 오버라이드된 메서드의 실제 호출 대상을 객체의 실제 타입에 따라 결정하는 가상 메서드 디스패치(`invokevirtual`)가 일어나는 계층.
이 노트는 주로 **언어 명세 계층**을 기준으로 서술하고, 바인딩 시점을 설명할 때만 컴파일러/런타임 계층을 언급합니다.

<a id="1-오버라이드override란"></a>

## 1. 오버라이드(Override)란?

- 상위 클래스(부모)가 정의한 인스턴스 메서드를, 하위 클래스(자식)가 **동일한 이름과 매개변수 목록**으로 다시 구현하는 것입니다.
- **상속 관계(`extends`) 또는 인터페이스 구현(`implements`) 관계에서만 성립**합니다. 아무 관계 없는 두 클래스의 동일한 메서드는 오버라이드가 아닙니다.
- **런타임 다형성(동적 바인딩)**: 참조 변수의 선언 타입이 아니라 **실제로 가리키는 객체의 타입**에 따라 실행할 메서드가 결정됩니다.

```java
Animal a = new Dog();
a.sound(); // 컴파일 타입은 Animal이지만, 실제 객체가 Dog이므로 Dog.sound() 실행
```

<a id="2-오버로드overload란"></a>

## 2. 오버로드(Overload)란?

- **같은 클래스 안에서(또는 상속 계층 전체에서)** 이름은 같고 **매개변수 목록(개수, 타입, 순서)이 다른** 메서드를 여러 개 정의하는 것입니다.
- **상속과 무관**합니다. 한 클래스 안에서만으로도 성립하며, 상속받은 메서드와 이름이 같고 매개변수만 다른 메서드를 하위 클래스에 추가하는 것도 오버로드입니다(상위 메서드는 그대로 상속됨).
- **컴파일 타임에 정적 바인딩**: 컴파일러가 인자의 **정적 타입(컴파일 시점 타입)**을 보고 가장 구체적으로(most specific) 일치하는 시그니처를 골라 호출을 확정합니다.
- **반환형만 다른 메서드는 오버로드가 불가능**합니다. 매개변수 목록이 같으면 컴파일러가 구분할 수 없기 때문이며, 컴파일 에러가 발생합니다.

```java
void print(int x) { }
int print(int x) { } // 컴파일 에러: 반환형만 다른 중복 메서드
```

    <tr><td>접근제어자</td><td>같거나 더 넓게만</td><td>자유</td></tr>
    <tr><td>`@Override` 적용</td><td>가능 (권장)</td><td>불가</td></tr>
    <tr><td>대표 예시</td><td>`Object.toString()` 재정의</td><td>`println(int)` / `println(String)` / `println(double)`</td></tr>
  </tbody>

<a id="4-코드-예시"></a>

## 4. 코드 예시

<a id="4-1-오버라이드-animal-dog"></a>

### 4-1. 오버라이드 (Animal → Dog)


```java
class Animal {
    String sound() { return "..."; }
}

class Dog extends Animal {
    @Override
    String sound() { return "멍멍"; } // 같은 시그니처로 재정의
}

Animal a = new Dog();
System.out.println(a.sound()); // "멍멍" — 실제 객체(Dog) 기준, 런타임 결정
```

<a id="4-2-오버로드-print-계열"></a>

### 4-2. 오버로드 (print 계열)


```java
class Printer {
    void print(int x)        { System.out.println("int: " + x); }
    void print(String x)     { System.out.println("String: " + x); }
    void print(int x, int y) { System.out.println("int,int: " + x + "," + y); }
}

Printer p = new Printer();
p.print(10);        // print(int) — 컴파일 시점에 확정
p.print("hello");   // print(String)
p.print(1, 2);      // print(int, int)
```

## 5. `@Override` 애노테이션 — "안 써도 되는" 이유와 "그래도 써야 하는" 이유

- 질문의 전제("안 쓰는 이유")를 바로잡으면, `@Override`는 **선택적(optional)**일 뿐이지 생략이 권장되는 것은 아닙니다. 오히려 **재정의하는 모든 메서드에 항상 붙이는 것이 모범 사례**입니다(Effective Java Item 40).
- **문법상 필수가 아닌 이유**: 컴파일러는 애노테이션이 없어도 상위 타입에 동일한 시그니처의 메서드가 있으면 이를 오버라이딩으로 인식하고 동적 바인딩 대상으로 처리합니다. 즉 동작에는 애노테이션이 필요 없습니다.
- **그래도 붙이면 얻는 것**:
- 메서드 이름이나 매개변수 타입에 오타가 있어 "재정의한 줄 알았지만 실제로는 새 메서드를 오버로드한" 실수를, **컴파일 에러로 즉시 검출**합니다.
- 상위 클래스의 메서드 시그니처가 나중에 변경되어 재정의 관계가 깨지면, 컴파일러가 알려줍니다.
- 코드를 읽는 사람에게 "이 메서드는 상위 계약을 구현/재정의한다"는 의도를 명시합니다.

- Java 6부터는 **인터페이스 구현 메서드에도 `@Override`를 붙일 수 있습니다** (Java 5에서는 클래스 상속 재정의에만 허용).

<a id="6-두-개념을-명확히-구분하기-위한-체크리스트"></a>

## 6. 두 개념을 명확히 구분하기 위한 체크리스트

새로 마주친 두 메서드가 오버라이드인지 오버로드인지 헷갈릴 때 다음을 순서대로 확인합니다.

1. **두 메서드가 상속/구현 관계인가, 같은 클래스(또는 계층) 안의 형제인가?**
- 상위-하위 관계 → 오버라이드 후보 / 같은 클래스 내 별개 정의 → 오버로드

1. **매개변수 목록이 완전히 동일한가?**
- 동일 → 오버라이드 후보 / 개수·타입·순서 중 하나라도 다름 → 오버로드

1. **호출 대상이 컴파일 시점 타입으로 정해지는가, 런타임 실제 객체로 정해지는가?**
- 컴파일 시점 → 오버로드 / 런타임 → 오버라이드

1. **`@Override`를 붙였을 때 컴파일되는가?**
- 컴파일 실패 → 오버라이드가 아님 (상위에 같은 시그니처 메서드가 없다는 뜻)

1. **반환형만 다른가?**
- 그렇다면 오버라이드도 오버로드도 아님 → 컴파일 에러

1. **`static` 메서드인가?**
- 상위와 같은 시그니처의 `static` 메서드는 오버라이드가 아니라 **메서드 하이딩(hiding)**. 동적 바인딩되지 않고 참조 타입 기준으로 호출됨

1. **접근제어자를 상위보다 더 좁혔는가?**
- 좁혔다면 오버라이드 규칙 위반 → 컴파일 에러

<a id="7-더-볼-것"></a>

## 7. 더 볼 것

- **메서드 하이딩**
`static` 메서드를 하위에서 같은 시그니처로 정의하면 오버라이드가 아닌 하이딩이 되며, 바인딩 규칙이 다릅니다.
- **공변 반환형(covariant return type)**
재정의 시 반환 타입을 더 구체적인 하위 타입으로 좁힐 수 있는 규칙으로, 빌더 패턴이나 `clone()` 재정의에서 유용합니다.
- **오토박싱이 섞인 오버로드 해석**
 `f(int)`와 `f(Integer)`, `f(Object)`가 함께 있을 때 컴파일러의 3단계 해석(박싱 없이 → 박싱/언박싱 허용 → 가변인자)으로 모호성이 발생할 수 있습니다.
