## 0. 정규화의 본질에 대한 실무적 고찰: "정규화를 어떻게 정의하고 기억할 것인가?"

<a id="1-데이터-효율을-위한-중복-제거라는-설명의-한계"></a>

### 1) "데이터 효율을 위한 중복 제거"라는 설명의 한계

필자 역시 정규화의 학술적 정의(1NF~5NF)를 무작정 달달 외우기보다는 `데이터 효율`, `중복 제거`, `관계 중시` 같은 직관적인 키워드로 기억하다 보니, 누군가에게 설명할 때도 흔히 *"데이터를 효율적으로 쓰기 위한 중복 제거 작업"* 정도로 축약해 설명할 때가 많았다.

하지만 이러한 설명은 데이터베이스에 대한 **충분한 배경지식이 이미 갖춰진 사람에게만 납득될 뿐**, 실제 데이터 모델링의 본질을 관통하는 온전한 설명이 되기는 어렵다.


<NotionDivider />

<a id="2-억지스러운-교과서적-테이블-예시가-낳는-오해"></a>

### 2) 억지스러운 교과서적 테이블 예시가 낳는 오해

1NF부터 5NF까지 각각의 단계에 딱 들어맞는 교과서적이고 인위적인 테이블 예시를 억지로 만들다 보면, 실제 실무 도메인과 괴리가 생겨 오히려 **설명의 난해함과 오해를 초래**하기 십상이다.


<NotionDivider />

<a id="3-rdb와-정규화의-진정한-본질-핵심-강조"></a>

### 3) RDB와 정규화의 진정한 본질 (핵심 강조)

> 🌟 **정규화의 본질적 정의**:


<NotionIndent>

**"RDB(관계형 데이터베이스)는 데이터 간의 관계성(Relationship)을 정의하여 정리하기로 약속된 체계이며,
그 약속에 따라 데이터의 책임과 경계를 짓고 올바르게 구분·관리(Data Governance)하는 작업을 정규화라 할 수 있다."**


</NotionIndent>

따라서 실무에서는 정규화의 수식이나 학술적 정의에 얽매이기보다, **"이 컬럼은 누구의 속성인가?"**, **"이 관계는 어떤 외래키(FK)로 맺어지고 어떻게 JOIN으로 복원되는가?"**라는 관점으로 테이블을 바라볼 때 가장 명쾌하게 데이터 구조를 설계할 수 있다.


<NotionDivider />

<a id="1-정규화-전-비정규-테이블-orderraw의-문제점"></a>

## 1. 정규화 전 비정규 테이블 (`ORDER_RAW`)의 문제점

쇼핑몰에서 주문 시스템을 처음 개발하며 단일 테이블에 모든 데이터를 몰아넣었다고 가정하자.


<NotionTable>
  <tbody>
    <tr><td>속성명</td><td>의미</td><td>데이터 예시</td></tr>
    <tr><td>`order_id`</td><td>주문번호</td><td>`1001`</td></tr>
    <tr><td>`user_id`</td><td>회원번호</td><td>`U01`</td></tr>
    <tr><td>`user_name`</td><td>회원명</td><td>김철수</td></tr>
    <tr><td>`user_phone`</td><td>전화번호</td><td>010-1111-2222</td></tr>
    <tr><td>`product_ids`</td><td>상품번호 목록</td><td>`P01,P02`</td></tr>
    <tr><td>`product_names`</td><td>상품명 목록</td><td>키보드, 마우스</td></tr>
    <tr><td>`quantities`</td><td>수량 목록</td><td>`1,2`</td></tr>
    <tr><td>`order_date`</td><td>주문일</td><td>`2026-08-25`</td></tr>
  </tbody>
</NotionTable>


```text
[ 구조적 문제점 ]
order_id = 1001
 ├─ 회원 정보 (user_id=U01, user_name=김철수, user_phone=010...)
 └─ 여러 상품 정보 (P01=키보드 수량 1개, P02=마우스 수량 2개)
 ➔ 한 행(Row)에 주문 + 회원 + 다중 상품 정보가 모두 섞여 있어 검색/수정/삭제가 불가능함
```


<NotionDivider />

<a id="2-1nf-제1정규형-컬럼의-원자값atomic-value-확보"></a>

## 2. 1NF (제1정규형): 컬럼의 원자값(Atomic Value) 확보

> 💡 **핵심 규칙**: **하나의 컬럼에는 더 이상 쪼갤 수 없는 단 하나의 값(원자값)만 저장한다.**


<NotionIndent>

➔ `product_ids = "P01,P02"`, `product_names = "키보드,마우스"` 같은 다중값/배열 컬럼을 행(Row) 단위로 분리한다.


</NotionIndent>

분리 후 테이블 (`ORDER_ITEM`)


<NotionTable>
  <tbody>
    <tr><td>`order_id` (PK)</td><td>`product_id` (PK)</td><td>`user_id`</td><td>`user_name`</td><td>`product_name`</td><td>`quantity`</td></tr>
    <tr><td>**1001**</td><td>**P01**</td><td>U01</td><td>김철수</td><td>키보드</td><td>1</td></tr>
    <tr><td>**1001**</td><td>**P02**</td><td>U01</td><td>김철수</td><td>마우스</td><td>2</td></tr>
    <tr><td>**1002**</td><td>**P01**</td><td>U02</td><td>이영희</td><td>키보드</td><td>1</td></tr>
  </tbody>
</NotionTable>

- **기본키(PK)**: `PRIMARY KEY (order_id, product_id)` 복합키 구성.
- **남아있는 문제**: 한 셀에 여러 상품이 들어가는 문제는 해결되었으나, `product_name`은 사실 `order_id`와는 무관하며 오직 `product_id`에 의해서만 결정된다 (product\_id \rightarrow product\_name).

<NotionDivider />

<a id="3-2nf-제2정규형-복합-pk의-부분-함수-종속성-제거"></a>

## 3. 2NF (제2정규형): 복합 PK의 부분 함수 종속성 제거

> 💡 **핵심 규칙**: **복합 PK를 사용하는 테이블에서, PK의 일부분에만 종속되는 속성을 별도 테이블로 분리한다 (완전 함수 종속화).**


<NotionIndent>

➔ `(order_id, product_id)` 중 `product_name`과 `price`는 `product_id`만 알면 되므로 `PRODUCT` 테이블로 분리한다.


</NotionIndent>

분리 후 테이블 (2NF 달성)

1) `PRODUCT` (상품 마스터 테이블)


<NotionTable>
  <tbody>
    <tr><td>`product_id` (PK)</td><td>`product_name`</td><td>`price`</td></tr>
    <tr><td>**P01**</td><td>키보드</td><td>50,000</td></tr>
    <tr><td>**P02**</td><td>마우스</td><td>30,000</td></tr>
  </tbody>
</NotionTable>

<a id="2-orderitem-주문-상세-매핑-테이블"></a>

#### 2) `ORDER_ITEM` (주문 상세 매핑 테이블)


<NotionTable>
  <tbody>
    <tr><td>`order_id` (PK, FK)</td><td>`product_id` (PK, FK)</td><td>`quantity`</td></tr>
    <tr><td>**1001**</td><td>**P01**</td><td>1</td></tr>
    <tr><td>**1001**</td><td>**P02**</td><td>2</td></tr>
    <tr><td>**1002**</td><td>**P01**</td><td>1</td></tr>
  </tbody>
</NotionTable>

<a id="조회-쿼리-join"></a>

### 조회 쿼리 (JOIN)


```sql
SELECT
    oi.order_id,
    oi.product_id,
    p.product_name,
    p.price,
    oi.quantity
FROM order_item oi
JOIN product p
    ON oi.product_id = p.product_id;
```

> 🎯 **실무 포인트**: 2NF는 복합 PK를 사용하는 **N:M 상세/매핑 테이블(`ORDER_ITEM`, `USER_ROLE`, `STUDENT_COURSE`)** 설계 시 필수적으로 점검하는 단계이다.


<NotionDivider />

<a id="4-3nf-제3정규형-일반-속성-간의-이행적-함수-종속성-제거"></a>

## 4. 3NF (제3정규형): 일반 속성 간의 이행적 함수 종속성 제거

<NotionIndent>

➔ 주문 테이블에서 `order_id -> user_id -> (user_name, user_phone)` 관계가 존재하므로, 회원 정보를 `USER` 테이블로 분리한다.


</NotionIndent>

<a id="5-완성된-쇼핑몰-표준-erd-구조와-통합-join"></a>

## 5. 완성된 쇼핑몰 표준 ERD 구조와 통합 JOIN

1NF부터 3NF까지 완료된 구조는 모든 엔티티가 자기 고유의 속성만을 소유하며, 관계는 외래키(FK)로 연결된다.


```text
       USER (회원 엔티티)
       --------------------
       PK user_id
          user_name
          user_phone
               │
               │ 1 : N (FK user_id)
               ▼
       ORDERS (주문 엔티티)
       --------------------
       PK order_id
       FK user_id
          order_date
               │
               │ 1 : N (FK order_id)
               ▼
     ORDER_ITEM (주문상품 매핑)
     --------------------
     PK,FK order_id
     PK,FK product_id
           quantity
               │
               │ N : 1 (FK product_id)
               ▼
      PRODUCT (상품 엔티티)
      --------------------
      PK product_id
         product_name
         price
```

<a id="쇼핑몰-주문-통합-조회-쿼리"></a>

### 쇼핑몰 주문 통합 조회 쿼리


```sql
SELECT
    o.order_id,
    o.order_date,
    u.user_id,
    u.user_name,
    p.product_id,
    p.product_name,
    p.price,
    oi.quantity
FROM orders o
JOIN user u
    ON o.user_id = u.user_id
JOIN order_item oi
    ON o.order_id = oi.order_id
JOIN product p
    ON oi.product_id = p.product_id;
```

> 🔑 **정규화와 조회의 핵심 진리**:


<NotionIndent>

**"정규화할수록 데이터를 저장하는 테이블은 책임 단위로 분리되고, 화면/API에서 조회할 때는 `JOIN`으로 다시 합친다."**


</NotionIndent>

```text

 ├─ order_id       ──> 주문 고유 식별자 (PK) ➔ ORDER 속성 O
 ├─ user_id        ──> 주문을 한 회원 연결 (FK) ➔ ORDER 관계 O
 ├─ order_date     ──> 주문 발생 시각 ➔ ORDER 속성 O
 │
 ├─ user_name      ──> "주문 테이블이 왜 회원 이름을 소유하는가?" ➔ USER 테이블로 이동 (3NF)
 ├─ user_phone     ──> "주문 테이블이 왜 전화번호를 소유하는가?" ➔ USER 테이블로 이동 (3NF)
 ├─ product_name   ──> "주문 테이블이 왜 상품명을 소유하는가?"   ➔ PRODUCT 테이블로 이동 (2NF)
 └─ category_name  ──> "주문 테이블이 왜 카테고리를 소유하는가?" ➔ CATEGORY 테이블로 이동 (3NF)
```

## 10. 비정규화(반정규화, Denormalization)에 대한 심층 고찰

<a id="1-정규화의-역설-과도한-join으로-인한-성능-병목"></a>

### ① 정규화의 역설: 과도한 JOIN으로 인한 성능 병목

정규화는 데이터 무결성과 CUD(생성·수정·삭제) 안정성을 극대화하지만, 대규모 트래픽 환경에서는 치명적인 조회 부하를 낳는다.

- 데이터를 한 번 조회할 때 5~10개의 테이블을 `JOIN`해야 함 ➔ **Disk I/O 폭증, 버퍼 풀 고갈, CPU 부하로 인한 슬로우 쿼리**.
<a id="2-비정규화-도입-기준-및-3대-기법"></a>

### ② 비정규화 도입 기준 및 3대 기법


```text
[ 비정규화 적용 기준 ]
 1. 읽기(Read) 비중이 90% 이상이고 응답 속도 최적화가 필수적인 테이블
 2. 인덱스 튜닝 및 Redis 캐싱으로도 목표 TPS 달성이 불가능한 구간
 3. 대규모 실시간 집계(통계, 카운트, 총액) 연산이 빈번한 구간
```

1. **중복 컬럼 역정규화**: `ORDERS` 테이블에 `product_name`을 복제하여 목록 조회 시 `JOIN` 제거.
1. **파생/집계 컬럼 추가**: `POST` 테이블에 `comment_count`, `like_count` 컬럼을 두고 댓글 작성 시마다 +1 갱신 (O(1) 조회).
1. **통계/히스토리 요약 테이블**: 매일 밤 정산 배치로 `DAILY_SETTLEMENT_SUMMARY` 요약 테이블 생성.
<a id="3-비정규화의-트레이드오프-데이터-정합성-방어-전략"></a>

### ③ 비정규화의 트레이드오프: 데이터 정합성 방어 전략

- **비용**: 조회 속도를 얻는 대신, **데이터 불일치(Inconsistency) 위험과 CUD 성능 저하**를 감수해야 함.
- **방어책**:
- 원본 갱신 시 중복 컬럼을 동기화하는 **애플리케이션 이벤트 / 트랜잭션 파이프라인(CDC)** 구축.
- 주기적인 데이터 불일치를 교정하는 **정합성 검증 배치(Reconciliation Batch)** 운영.
