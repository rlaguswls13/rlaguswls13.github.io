## <strong>0. 논의 범위 획정</strong>

"쿼리가 느리다"는 신고는 최소 4개의 서로 다른 원인을 뭉뚱그린 표현입니다. 진단은 아래 계층을 <strong>위에서 아래로 하나씩 배제</strong>하며 좁힙니다.


```text
[클라이언트 체감]   브라우저/앱 응답 대기 = 큐잉 + 서버 처리 + 직렬화 + 전송
      │
[애플리케이션 + 드라이버]   ORM 매핑, N+1, prepared statement 플랜, fetch size
      │
[네트워크 + 커넥션 풀]   RTT, 풀 acquire 대기, 커넥션 누수, keepalive, 락 대기
      │
[DB 내부]   파싱/플랜 + 스캔 + 조인 + 정렬 + I/O
```

핵심 질문 두 가지:

1. <strong>"쿼리 자체가 느린가"</strong> 를 어떻게 검증하는가 → 1~3장
1. <strong>DB 내부가 느리다면</strong> 무엇을 확인하는가 (index / pagination / partitioning / sharding) → 4~5장

<a id="12-앱에서-tapp-재는-코드-java-예시"></a>

### <strong>1.2 앱에서 T_app 재는 코드 (Java 예시)</strong>


```java
long t0 = System.nanoTime();
List<OrderRow> rows = jdbcTemplate.query(SQL, mapper, params);
long tQuery = System.nanoTime();
List<OrderDto> dto = rows.stream().map(this::toDto).toList();  // 매핑 비용 분리 측정
long tMap = System.nanoTime();

log.info("query={}ms map={}ms rows={}",
        (tQuery - t0) / 1_000_000,
        (tMap - tQuery) / 1_000_000,
        rows.size());
```

`query`는 20ms인데 전체 API가 800ms라면 매핑·직렬화·다른 호출을 의심합니다.

## <strong>2. 2단계 - DB 바깥(네트워크·커넥션·풀) 점검</strong>

<a id="21-커넥션-풀-고갈-쿼리는-빠른데-요청이-느림"></a>

### <strong>2.1 커넥션 풀 고갈 - "쿼리는 빠른데 요청이 느림"</strong>

풀에서 커넥션을 못 받아 대기하면, 쿼리 실행 시간과 무관하게 요청이 느려집니다.


```java
// HikariCP: acquire 대기 시간·활성 커넥션 메트릭 노출
HikariDataSource ds = ...;
HikariPoolMXBean pool = ds.getHikariPoolMXBean();
log.info("active={} idle={} waiting={} total={}",
        pool.getActiveConnections(),
        pool.getIdleConnections(),
        pool.getThreadsAwaitingConnection(),   // 이 값이 0보다 크면 풀 부족 신호
        pool.getTotalConnections());
```


```text
# 진단용: 커넥션을 200ms 안에 못 받으면 예외로 빠르게 실패시켜 병목을 표면화
spring.datasource.hikari.connection-timeout=200
spring.datasource.hikari.leak-detection-threshold=5000   # 5초 넘게 안 반환된 커넥션 경고
```


```sql
-- DB 쪽에서 현재 연결 상태 확인
-- PostgreSQL
SELECT state, count(*) FROM pg_stat_activity GROUP BY state;
--  idle in transaction 이 많으면 → 앱이 트랜잭션을 안 닫고 있음 (커넥션 누수의 전형)

-- MySQL
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
SELECT @@max_connections;
```

<a id="22-커넥션-누수-진단"></a>

### <strong>2.2 커넥션 누수 진단</strong>


```text
증상: active 커넥션 수가 시간에 따라 우상향, 재기동하면 정상 → 서서히 다시 증가
확인:
  1) HikariCP leak-detection-threshold 로그의 스택트레이스 → 반환 안 한 코드 위치
  2) pg_stat_activity 에서 state='idle in transaction', query_start 오래된 세션
  3) 트랜잭션 경계(@Transactional) 밖에서 커넥션을 수동 획득 후 close() 누락
조치: try-with-resources / @Transactional 범위 정리, 외부 API 호출을 트랜잭션 밖으로
```

<a id="23-n1-쿼리-목록-api만-느림"></a>

### <strong>2.3 N+1 쿼리 - "목록 API만 느림"</strong>


```text
로그 관찰:
  SELECT * FROM orders WHERE ordered_at >= ?          (1회, 50건)
  SELECT * FROM shipments WHERE order_id = ?           (50회)   ← N+1
  SELECT * FROM customers WHERE id = ?                 (50회)   ← N+1
=> 쿼리 각각은 1ms지만 101회 × RTT(2ms) = 200ms+
```


```java
// JPA: fetch join 또는 @EntityGraph 로 한 번에
@Query("SELECT o FROM Order o JOIN FETCH o.shipment JOIN FETCH o.customer " +
       "WHERE o.orderedAt >= :from")
List<Order> findWithDetails(@Param("from") LocalDateTime from);

// 또는 배치 IN 조회
// SELECT * FROM shipments WHERE order_id IN (:ids)   -- 50건을 1회로
```

### <strong>2.4 fetch size / 스트리밍 - "결과가 큰데 앱 메모리·시간 급증"</strong>

```java
// JDBC 기본 fetch size는 드라이버마다 다름.

// MyBatis

```

<a id="25-락-대기-특정-시간대에만-느림"></a>

### <strong>2.5 락 대기 - "특정 시간대에만 느림"</strong>


```sql
-- PostgreSQL: 무엇이 무엇을 막고 있는가
SELECT blocked.pid   AS blocked_pid,
       blocked.query AS blocked_query,
       blocking.pid  AS blocking_pid,
       blocking.query AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));

-- MySQL 8
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM sys.innodb_lock_waits;
```


```text
원인 예: 배치가 긴 트랜잭션으로 UPDATE 락 보유 → 화면 조회 SELECT ... FOR UPDATE 가 대기
조치: 트랜잭션 범위 축소, 배치를 청크 커밋으로, 조회는 FOR UPDATE 제거 또는 SKIP LOCKED
```

<a id="3-cli는-빠른데-앱에서만-느린-경우-플랜바인드"></a>

## <strong>3. CLI는 빠른데 앱에서만 느린 경우 (플랜·바인드)</strong>


```text
현상: psql에서 SELECT ... WHERE status = 'PAID' → 5ms
      앱(PreparedStatement, 바인드 파라미터) → 900ms

원인 후보:
  1) Generic Plan: PG는 prepared statement를 5회 실행 후 파라미터 무관 일반 플랜으로 고정.
     특정 값에서만 유리한 인덱스를 안 타게 될 수 있음.
  2) 파라미터 데이터 타입 불일치: 컬럼은 varchar인데 바인드가 다른 타입 → 인덱스 미사용, 암시적 캐스팅.
  3) 바인드 변수 sniffing (SQL Server/Oracle): 첫 실행 파라미터 기준 플랜이 캐시됨.

확인/조치:
  - PG: plan_cache_mode = force_custom_plan (세션/함수 단위)
  - 타입 명시 캐스팅, 파라미터 타입을 컬럼과 일치
  - 편차 큰 쿼리는 리터럴 분기 또는 힌트/플랜 고정
```


```sql
-- PG: prepared statement가 실제로 어떤 플랜을 쓰는지
PREPARE p1(text) AS SELECT * FROM orders WHERE status = $1;
EXPLAIN (ANALYZE) EXECUTE p1('PAID');
```

<a id="42-인덱스가-있는데-안-타는-대표-패턴"></a>

### <strong>4.2 "인덱스가 있는데 안 타는" 대표 패턴</strong>


```sql
-- (X) 컬럼에 함수 적용 → 인덱스 무력화
WHERE DATE(ordered_at) = '2026-09-10'
-- (O) 범위 조건으로 (sargable)
WHERE ordered_at >= '2026-09-10' AND ordered_at < '2026-09-11'

-- (X) 앞부분 와일드카드
WHERE name LIKE '%kim'
-- (O) 뒷부분만 / 전문검색 인덱스 / reverse 인덱스
WHERE name LIKE 'kim%'

-- (X) 타입 불일치 (bigint 컬럼에 문자열 바인드)
WHERE customer_id = '12345'
-- (O) 타입 일치
WHERE customer_id = 12345

-- (X) OR로 서로 다른 컬럼
WHERE status = 'PAID' OR customer_id = 10
-- (O) UNION ALL 분리 또는 각각 인덱스

-- 낮은 선택도: status 값이 2종뿐이면 인덱스보다 Seq Scan이 빠를 수 있음(정상)
```

<a id="43-복합-인덱스-컬럼-순서"></a>

<a id="5-case-report-db-내부-병목-유형별"></a>

## <strong>5. Case Report - DB 내부 병목 유형별</strong>

<a id="51-case-a-인덱스-부재로-인한-full-scan"></a>

### <strong>5.1 Case A - 인덱스 부재로 인한 Full Scan</strong>


```text
증상: SELECT ... WHERE email = ?  → 2.4초 (users 800만 행)
EXPLAIN: Seq Scan on users, Rows Removed by Filter: 7,999,999
```


```sql
-- 조치
CREATE INDEX ix_users_email ON users(email);
-- 재측정: Index Scan, Execution Time 2,400ms → 1.2ms
```

<a id="52-case-b-offset-페이지네이션이-뒤로-갈수록-느림"></a>

### <strong>5.2 Case B - OFFSET 페이지네이션이 뒤로 갈수록 느림</strong>


```text
증상: 1페이지 8ms, 5000페이지(OFFSET 100000) 1,900ms
원인: LIMIT 20 OFFSET 100000 은 앞 100,000행을 읽고 버린 뒤 20행 반환
```


```sql
-- (X) 오프셋 방식
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 100000;

-- (O) 키셋(seek) 페이지네이션: 직전 페이지 마지막 키를 커서로
SELECT * FROM orders
WHERE id < :last_seen_id          -- 첫 페이지는 조건 생략
ORDER BY id DESC
LIMIT 20;
-- 재측정: 어느 페이지든 8~10ms (인덱스 진입점만 바뀜)

-- 정렬 키가 유니크하지 않으면 복합 커서
WHERE (ordered_at, id) < (:last_ordered_at, :last_id)
ORDER BY ordered_at DESC, id DESC
LIMIT 20;
```

<a id="53-case-c-반복-집계-쿼리-요약-테이블"></a>

### <strong>5.3 Case C - 반복 집계 쿼리 (요약 테이블)</strong>


```text
증상: 대시보드가 매 요청마다 "일자별 매출 합계"를 orders 전체 스캔으로 계산 → 3초
```


```sql
-- (O) 사전 집계 테이블 + 증분 갱신
CREATE TABLE daily_sales (
    sales_date DATE PRIMARY KEY,
    total_amount DECIMAL(18,2),
    order_count INT
);

-- 배치(또는 트리거/CDC)로 증분 반영
INSERT INTO daily_sales (sales_date, total_amount, order_count)
SELECT DATE(ordered_at), SUM(amount), COUNT(*)
FROM orders
WHERE ordered_at >= :since        -- 마지막 집계 시점 이후만
GROUP BY DATE(ordered_at)
ON CONFLICT (sales_date)
DO UPDATE SET total_amount = EXCLUDED.total_amount,
              order_count  = EXCLUDED.order_count;

-- 조회: SELECT * FROM daily_sales WHERE sales_date BETWEEN ? AND ?  → 1ms
-- 또는 PostgreSQL MATERIALIZED VIEW + REFRESH ... CONCURRENTLY
```

<a id="54-case-d-단일-거대-테이블-파티셔닝"></a>

### <strong>5.4 Case D - 단일 거대 테이블 → 파티셔닝</strong>


```text
판단 기준: 데이터가 매우 크지만(수억 행) 쓰기·커넥션 부하는 한 인스턴스가 감당 가능,
           조회가 특정 키(주로 기간)로 잘 잘림 → 파티셔닝
```


```sql
-- PostgreSQL: 월 단위 range 파티션
CREATE TABLE events (
    id BIGINT, occurred_at DATE NOT NULL, payload JSONB
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09 PARTITION OF events
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
CREATE TABLE events_2026_10 PARTITION OF events
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 조회에 파티션 키를 포함해야 pruning 발생
EXPLAIN SELECT * FROM events WHERE occurred_at >= '2026-09-10' AND occurred_at < '2026-09-11';
--> events_2026_09 하나만 스캔 (나머지 파티션 제외)

-- 효과: 오래된 파티션은 DETACH/DROP 으로 즉시 삭제(대량 DELETE 회피),
--       인덱스가 파티션별로 작아져 캐시 효율 상승
```

<a id="55-case-e-단일-서버-쓰기용량-한계-읽기-복제본-후-샤딩"></a>

### <strong>5.5 Case E - 단일 서버 쓰기·용량 한계 → 읽기 복제본 후 샤딩</strong>


```text
escalation 순서 (아래로 갈수록 운영 복잡도 급증):
  쿼리·인덱스 튜닝 → 캐싱/요약 테이블 → 읽기 복제본 분산 → 파티셔닝 → 샤딩

읽기 복제본: 조회 트래픽을 replica로. 복제 지연(replication lag) 허용 가능한 화면만.
샤딩: 단일 인스턴스의 쓰기 TPS·저장 용량·커넥션 한계에 도달했을 때. 최후 수단.
```


```sql
-- 애플리케이션 레벨 샤딩 예: customer_id 기준 4개 샤드
-- shard_index = customer_id % 4
--   shard0: db-0,  shard1: db-1,  shard2: db-2,  shard3: db-3

-- 크로스 샤드 조인/트랜잭션은 불가에 가까움 →
--   1) 샤드 키를 대부분의 조회가 공유하도록 설계 (여기서는 customer_id)
--   2) 집계는 각 샤드에서 부분 집계 후 애플리케이션에서 병합(scatter-gather)
--   3) 핫 샤드 방지: 해시 기반 분산, 특정 대형 고객 전용 샤드 분리
```

<a id="6-진단-순서-요약-runbook"></a>

## <strong>6. 진단 순서 요약 (Runbook)</strong>


```text
1. APM/로그로 T_client, T_app, T_db 분리
     └ T_app ≫ T_db → 2번으로 (DB 바깥)
     └ T_db 큼      → 4번으로 (DB 내부)

2. DB 바깥
   ├ HikariCP: threadsAwaitingConnection > 0 → 풀 크기 / 누수 (leak-detection 로그)
   ├ pg_stat_activity: 'idle in transaction' 다수 → 트랜잭션 미종료
   ├ 목록 API만 느림 → N+1 (fetch join / IN 배치)
   ├ 결과 큼 → fetch size / 스트리밍
   ├ 특정 시간대 → 락 대기 (pg_blocking_pids)
   └ CLI만 빠름 → prepared statement generic plan / 타입 불일치 → 3번

3. 플랜·바인드
   └ force_custom_plan, 타입 캐스팅 일치, 편차 큰 쿼리 분기

4. DB 내부: EXPLAIN (ANALYZE, BUFFERS)
   ├ estimated vs actual 10배+ → ANALYZE / 통계
   ├ 큰 테이블 Seq Scan → 인덱스 (sargable 재작성)
   ├ Sort external Disk → work_mem, 인덱스로 정렬 제거
   └ Nested Loop loops 큼 → 조인 순서 / 인덱스

5. 구조 개선 (위에서 안 되면 순서대로)
   OFFSET 페이징 → 키셋 페이징
   반복 집계     → 요약 테이블 / MATERIALIZED VIEW
   거대 테이블   → 파티셔닝 (조회에 파티션 키 포함)
   읽기 과부하   → 읽기 복제본
   쓰기·용량 한계 → 샤딩 (최후, 크로스 샤드 제약 감수)
```
