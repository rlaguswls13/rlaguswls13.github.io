## 핵심 요약

본 문서는 국비지원 교육과정의 중간 점검 팀 프로젝트([YouWin Repository](https://github.com/rlaguswls13/youwin))를 총괄 리딩하며 적용한 <strong>애자일 칸반(Kanban) 작업 관리, Git Flow 브랜치 보호 전략, AI 기반 UI/UX 표준화 및 페어 프로그래밍, 그리고 신뢰 중심의 팀 그라운드 룰(Working Rules)</strong> 구축 사례를 정리한다.

단순한 코드 구현을 넘어, 팀원들이 순수 Java MVC 패턴의 CRUD 아키텍처와 JS 비동기 데이터 통신을 안정적으로 구현할 수 있도록 인프라/프론트엔드 장벽을 낮추고, 체계적인 협업 프로세스를 통해 성공적인 결과물을 도출한 실전 프로젝트 관리 방법론입니다.

## 2. 애자일 칸반(Kanban) 기반 작업 관리 체계

칸반보드는 복잡한 이슈 추적 도구(Jira, Slack 등)의 핵심 원리를 가볍고 직관적으로 적용하여 프로젝트의 흐름(Flow)과 병목(Bottleneck)을 실시간으로 가시화하는 최적의 도구이다.


```text
[Backlog / Ready] ──> [In Progress] ──> [In Review / Test] ──> [Done]
  (일간/주간 등록)       (1인 1티켓 담당)      (로컬 충돌 해결 & 검증)     (main 병합 완료)
```

<a id="1-티켓팅-및-작업-방식-task-management"></a>

### 1)  티켓팅 및 작업 방식 (Task Management)

1. <strong>일간/주간 단위 Task 일괄 등록</strong>: 스프린트 단위로 팀원 각자가 수행할 작업을 사전에 등록하고, 애자일 원칙에 따라 유연하게 수정·취소·생성.
1. <strong>1인 1티켓(Single Ownership) 원칙</strong>:
- 티켓 추적의 혼선을 방지하기 위해 <strong>하나의 티켓은 1명의 담당자가 작성 ➔ 진행 ➔ 완료 로그 기록</strong>을 전담.
- 다수의 인원이 하나의 티켓에 얽혀 히스토리가 꼬이는 현상을 원천 방지.
- 부득이하게 복수 인원이 티켓을 공동 처리해야 할 경우, 작업 내역과 변경 사유에 대한 상세 로그(Log) 작성을 의무화.

1. <strong>업무 범위 격리(Scope Guarding)</strong>:
- 칸반 보드 내 논의는 프로젝트 범위(Scope) 내 작업에 한정.
- 외부 잡무나 프로젝트 무관 리소스가 칸반에 유입되어 우선순위와 일정을 왜곡하는 현상을 방지.

## 4. 개발 협업 그라운드 룰 (Working Rules) & Git Flow

소스코드의 무결성을 유지하고 병합 충돌(Merge Conflict)로 인한 생산성 저하를 방지하기 위해 명확한 Git Flow 규칙을 수립·적용하였다.


```text
   feature/name-a ─────┐
                       ▼ (로컬에서 충돌 해결 후 검증)
  main ────────────────●─────────────────────────────> (안정된 배포 브랜치)
                       ▲ (Direct Push 금지)
   feature/name-b ─────┘
```

## 5. 코어 타임 및 심리적 안전감(Psychological Safety) 기반 팀 문화

<a id="1-집중-작업-기간-및-코어-타임core-time"></a>

### 1) 집중 작업 기간 및 코어 타임(Core Time)

- <strong>집중 몰입 기간</strong>: 7월 20일 ~ 7월 31일 (약 2주간의 스프린트)
- <strong>평일 코어 타임 (월~목)</strong>:
- `18:00 ~ 18:30`: 석식 및 리프레시
- `18:30 ~ 21:00`: 오프라인/온라인 집중 합동 작업
- <strong>자율 퇴근제 도입</strong>: 당일 할당된 Task를 완료하고 추가 질의사항이 없는 팀원은 19:00~20:00에 자유롭게 퇴근할 수 있도록 보장하여 불필요한 눈치보기성 잔업 배제.

- <strong>주말 온라인 헬프데스크 (토~일)</strong>:
- `10:00 ~ 17:00`: Discord 음성 채널 상시 오픈.
- 개발 중 막히는 블로커(Blocker) 발생 시 언제든 접속하여 실시간 화면 공유 및 질의응답 진행 (PL 상시 대기 및 페어 프로그래밍 지원).

<a id="2-상호-존중과-신뢰-기반-커뮤니케이션"></a>

### 2) 상호 존중과 신뢰 기반 커뮤니케이션

- <strong>호칭 규정</strong>: 상호 간 친밀도에 따라 편한 사이는 `'형'`, 공적인 자리나 어색한 관계에서는 반드시 <strong>`'님'`</strong>으로 호칭을 통일하여 심리적 안전감과 예의를 동시에 확보.
- <strong>참여 및 일정 공유</strong>: 회의나 공동 작업 불참 시 당일이라도 사전 공유 원칙 준수. 벌칙이나 강제 규정 대신 <strong>'신뢰와 상호 예의'</strong>를 중심 가치로 두어 팀 결속력 유지.

## 6. 기술적 성과 및 교훈 (Retrospective)

<a id="1-성공-요인-key-success-factors"></a>

### 1) 성공 요인 (Key Success Factors)

1. <strong>AI 페어 프로그래밍을 통한 프론트엔드 표준화</strong>: 초보 팀원들이 UI 퍼블리싱에 시간을 낭비하지 않고 Java MVC 백엔드 아키텍처 이해와 데이터 흐름 제어에 집중할 수 있었음.
