마지막 회사를 퇴사하면서 개선하거나 추가해보고 싶은 기능을 직접 구현해보려는 생각을 했습니다. 그중에 Email과 Push는 현재 TCP 통신을 사용하고 무료로 쉽게 이용할 수 있기 때문에 개발을 시작해봤습니다.

Ai 1:1로 사용할 때는 생각보다 쉽게 개별 모듈 생성은 쉽게 만들었습니다.

그런데, 욕심에 mssaging platform이라는 서비스로 배포할 수 있는 repo생성을 목적으로 각 모듈을 합치고 react로 프론트를 생성을 진행을 했는데, git 다이벌전트가 발생하고 그 사이에 모듈간 의존성이 꼬이면서 소스 유실이 하나씩 발생이되서 테스트 자체가 안되기 시작했습니다. 엎친데 덮친격이라고 컴퓨터가 7년이 지난서 그런건지 점점 느려지더니 반복적인 화면 멈춤도 발생하기 시작했습니다. 그래서 초반에는 불필요한 보안프로그램 삭제 → docker/하이퍼바이저 같은 리소스 격리하여 사용하는 프로그램 삭제 → 디스크 정리 순으로 진행을 해서 버티다가, 멈추는게 나아질 기미가 보이지 않아서 포맷을 하는 것을 마음 먹고 지난 프로젝트 백업 및 github로 다 올렸다는 생각에 컴퓨터 포맷을 진행 했습니다. 그런데 왠걸 백업은 잘 진행되었고, 컴퓨터 백업후에는 컴퓨터가 정상적으로 돌아와서 평온한 마음으로 모듈 통합을 진행하는데, git 이력이 github에 다 올라가지 않았었고 통합과정에서 소스 유실이 실제로 발생했던 겁니다. 그래서 눈물을 머금고 작업전에 작성했던 프로젝트 명세 기반과 남은 소스 이력을 토대로 ai를 활용하여 복원 작업을 진행을 시작했습니다.

처음에는 막막했는데 노션에 작성해둔 명세서가 현재 사용중인 wiki의 역할을 대체 하면서 유실되었던 소스가 100프로는 아니지만, 구현했던 기능은 어느정도 까지 진행이 되었고 현시점 (7월 28일) 기준으로 50% 정도, 복원이 진행된 걸로 보였습니다. 꾸준히 하면 9월에는 실제 배포해서 간이로 클로즈 베타 서비스를 진행해볼 수 있을 것으로 예상하고 있습니다.



앞으로는 github와 같은 원격저장소에 실제로 올라가있는지 report를 받거나 ai notice를 통해서 주요 프로젝트 알림 서비스를 받아서 백업 하는 노력을 남겨야할 것을 같습니다. 그리고, 



[개발 환경에 대해서 정리]

발송모듈 - 컨텍스트모듈 - 설정모듈로 역할을 정확하게 나누고, 각 기능을 구현했습니다. 당시 환경은 JAVA21, SpringBoot의 webflux (non-blocking), Spring batch, ThreadExactor를 적극적으로 활용 했습니다. 

초기 발송모듈은 DB 접근 없이, TCP 통신을 다이렉트로 context(전송데이터)를 받거나 MQ 미들웨어를 통해서 전달 받은 데이터를 push 메세지는 firebase, APNS 서버로 전달 email은 SMTPS(587, 465 포트) 또는 표준 (25 포트)로 각 메일서버(gmail, naver 기준으로 테스트진행)했습니다. 

컨텍스트 모듈은 push는 pushwoosh라는 회사의 템플릿 유형을 벤치마킹하고, 이전 회사동료의 도움을 받아서 noti, 캐러셀, 버튼형 등으로 템플릿을 상세화하여 테스트 진행을 해보고, 실제 android 테스트 환경에서 전달 받아서 활용할 수 있는 부분까지 확인 했었습니다. 이메일은 [https://datatracker.ietf.org/doc/html/rfc5321](https://datatracker.ietf.org/doc/html/rfc5321) ai 학습을 시키고, 이전 도메인 지식을 활용하여 drmac, ssl적용, dkim 적용, conanical 등을 손쉽게 적용할 수 있었습니다.

마지막으로 설정 모듈의 경우는 각 모듈마다 설정파일로 고정된 값을 동적으로 활요하기위해서 spring cloud의 config 서버를 세팅을 활용하여 jvm 실행시 고정되었던 것을 활용해서 동적 설정 서버를 만들어봤습니다.

위 모듈을 개별적으로 docker-compose로 컨테이너 환경으로 테스트를 했을때 성공적으로 발송되는 것까지 확인을 헀는데 증빙자료를 따로 준비를 못해서 너무 아쉽습니다.
